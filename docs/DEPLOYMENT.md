# Deployment and operations

## Development

Run the README Docker commands. Only Nginx (localhost:8080) and Mailpit
(localhost:8025) are published. PostgreSQL, Redis, Django, Node gateway and Next.js
communicate on the private Compose network. Secrets are generated by
`scripts/init_env.py`; `.env` is ignored. `docker compose logs worker beat gateway`
helps inspect operational failures. No message bodies or key secrets are logged by
application task handlers. Do not enable request/body debug logging for live data.

## Staging and production

Use separate hosts/accounts/databases, Redis volumes and secrets for staging and
production. Do not copy customer credentials into sandbox projects. Set DEBUG=0,
PUBLIC_URL, exact ALLOWED_HOSTS, CSRF_TRUSTED_ORIGINS and CORS_ALLOWED_ORIGINS.
Configure authenticated SMTP and TLS, supported META_GRAPH_VERSION, vetted
OTP_TEMPLATE_NAMES, and explicit WEBHOOK_ALLOWED_HOSTS. GEMINI_API_KEY and
GEMINI_MODEL are optional. Never reuse the example values.

Provide an ACME-managed certificate as `tls/fullchain.pem` and `tls/privkey.pem`.
The certificate private key must be readable by the proxy and protected from
other accounts. The repository does not obtain or renew certificates for you.
Docker Compose 2.24.4+ is required for the production override syntax:

```sh
docker compose -f compose.yaml -f compose.production.yaml up --build -d
docker compose exec backend python manage.py check --deploy
```

Nginx redirects HTTP to HTTPS. Secure cookies/HSTS apply with DEBUG=0. Production
sets TRUST_PROXY=1: Nginx overwrites X-Forwarded-Proto and X-Real-IP. Never expose
Django directly when this flag is set. IP allowlisting/rate limits use the direct
peer in development and the trusted proxy address in this mode. If adding an
upstream load balancer, explicitly configure Nginx real-IP trust for its known
addresses; do not trust arbitrary forwarded headers. Redis is private, AOF is
enabled, `appendfsync always` favors duplicate-send safety, and eviction is disabled.
Use managed durable Redis and PostgreSQL with backups for larger deployments.

Run migrations once per release before increasing backend/worker replicas. Run
one Beat scheduler. Review status/queue metrics before and after upgrades. Pin
container images by digest for your release process after security scanning; the
provided tags are development defaults, not a supply-chain attestation.

## Official Meta onboarding

Create/register a Meta business app and WhatsApp Business Account using Meta's
supported process. Obtain the correct phone-number ID, permissions and system-user
access token. In a live WhatsBridge project, create a Meta connection and submit
credentials with Onboard. The gateway validates the phone ID against Graph API
before marking connected. This is credential onboarding, **not embedded signup**.
Configure Meta webhook callback `/api/providers/meta/CONNECTION_UUID` and the
matching verify token, subscribe the business account/app to messaging events,
and test signed callbacks on staging. Approve templates in WhatsApp Manager.
Only verified AUTHENTICATION templates belong in OTP_TEMPLATE_NAMES.

The adapter implements the HTTP contract and is covered by mocked tests. No live
Meta token/account was available for this delivery. Validate your selected Graph
API version, app permissions, template button structure, language, and webhook
subscription before live use. Provider account restrictions still apply.

## Health and monitoring

`/health` checks database and cache. Internal gateway `/health` checks Redis.
`/metrics` is superuser-session protected; it reports queued messages and dead
webhooks. The platform dashboard reports worker dispatch heartbeat and failures.
Monitor Beat/worker container liveness, queue age, accepted-without-receipt age,
unknown sends, dead webhook counts, DB storage, and Redis memory. This is baseline
instrumentation, not a complete Prometheus/Grafana deployment.

## Failure recovery

- `queued`: inspect Beat, worker, Redis and scheduled_at.
- `unknown`: a send may have reached Meta. Compare provider records and callbacks;
  never blanket-reset unknown sends to queued. Gateway Redis claims intentionally
  retain unknown outcomes. No customer-facing force-resend action exists.
- `failed`: inspect redacted error and consent/connection state. Five safe transient
  attempts form the message dead letter. Create a new deliberate request only
  after resolving the cause.
- Webhook dead letters: fix endpoint, inspect history, then retry with its delivery
  UUID. Keep receiver replay storage intact.
- Failed workflows: inspect cursor/history and side effects. Retry is bounded;
  external HTTP/webhook/AI failures require reconciliation and a deliberate new run.
- Disconnect/revoke deletes stored provider credentials; re-onboard to reconnect.

## Backup, retention, secrets

`scripts/backup.sh` creates a restrictive-permission pg_dump. Encrypt and copy it
off-host. Test `scripts/restore.sh FILE` against an **empty, isolated** database;
never restore over live data without a reviewed recovery plan. Back up Redis AOF,
the Fernet key and service secrets separately, encrypted with restricted access.
Restoring DB without its credential key makes encrypted records unreadable.

Nightly retention clears message content after 90 days, AI conversations after
90 days, expired OTP hashes after 24 hours, and old successful webhook deliveries.
Usage/idempotency/audit records remain; adapt retention to your legal requirements.
Contact deletion is available through the API; full customer data export/erasure
or account closure is not implemented. Deletion must consider retained message
phone numbers and audit data. No automatic encryption-key rotation command is
included: back up, re-encrypt records under a new key transactionally, and test
recovery before retiring the old key.

## Release gate

Before treating this as production-ready: run Compose in staging, run PostgreSQL
concurrency/load tests, exercise Redis/Celery restarts, obtain/renew valid TLS,
validate real Meta onboarding and delivery/read/inbound callbacks, prove backup
restores, test SMTP and 2FA recovery, review dependency/container scans, establish
abuse review and data lifecycle processes, and complete an independent security
review. The local verification report does not substitute for these checks.
